# «Рядом» — помощь с госуслугами в MAX

Mini app для MAX, в котором человек заполняет заявление на госуслугу и в любой момент может позвать помощь: близкого, сотрудника МФЦ или цифрового сотрудника. Помощник подключается к той же форме, говорит голосом и показывает, куда нажать, но не видит личных данных и не может отправить заявление за человека.

- Рабочая версия: `https://max-hackathon.explainlaw.ru`
- Бот в MAX: `https://max.ru/t562_hakaton_max_bot`

## Назначение

Пожилым людям и тем, кто плохо ориентируется в цифровых сервисах, трудно самостоятельно пройти длинную форму госуслуги. Обычно им помогают близкие, но для этого приходится диктовать по телефону СНИЛС, номер счёта и коды из SMS или передавать телефон в чужие руки. «Рядом» позволяет помочь удалённо и безопасно:

- помощник видит, на каком шаге человек, и слышит его голос;
- показывает поле подсветкой или указателем;
- личные данные (ФИО, СНИЛС, адрес, счёт, коды) скрыты от него на стороне сервера;
- отправить заявление может только сам владелец;
- встреча записывается, и при следующей подаче той же услуги на нужном шаге появляется подсказка «Как вы решали это раньше».

## Основной пользовательский сценарий

1. Людмила открывает mini app из бота MAX и начинает заявление «Компенсация расходов на оплату ЖКУ» (7 шагов).
2. На шаге, где непонятно, она нажимает «Позвать помощь» и выбирает близкого, сотрудника МФЦ или цифрового сотрудника.
3. Близкому приходит сообщение бота с кнопками «Подключиться» и «Сейчас не могу». Если он занят, Людмила сохраняет черновик, а когда близкий освободится, зовёт его снова одним нажатием.
4. Помощник подключается, они разговаривают голосом. Помощник подсвечивает поля; вместо СНИЛС и адреса он видит «███ заполнено».
5. Людмила сама вводит код из SMS и отправляет заявление.
6. Запись встречи сохраняется: её можно прослушать в истории, а при следующей подаче та же подсказка появится на нужном шаге.

## Состав и архитектура

| Сервис в `docker-compose.yml` | Что делает | Сборка |
|---|---|---|
| `nginx` | Единая точка входа на `http://localhost:3000`: отдаёт frontend, проксирует `/api` и WebSocket `/ws` в API | образ `nginx:1.27-alpine`, конфиг `deploy/nginx/local.conf` |
| `frontend` | Mini app: React 19, TypeScript, Vite, MAX UI, клиент LiveKit | `frontend/Dockerfile` |
| `api` | Backend: FastAPI, REST `/api/v1`, WebSocket встречи, миграции при старте | `backend/Dockerfile` |
| `postgres` | PostgreSQL 16: пользователи, заявления, встречи, журнал | образ `postgres:16` |
| `livekit` | Голосовые комнаты (WebRTC) | образ `livekit/livekit-server:v1.13.7` |
| `egress` | Записывает разговор в файл `recordings/<id>.ogg` | образ `livekit/egress:v1.14.1` |
| `recordings-init` | Один раз перед Egress выставляет права на каталог записей | образ `busybox:1.37` |
| `redis` | Очередь заданий между LiveKit и Egress | образ `redis:7-alpine` |
| `agent` | Цифровой сотрудник: LiveKit Agents, Yandex SpeechKit и модель Qwen | `agent/Dockerfile` |

```text
браузер / MAX WebView
   │ http://localhost:3000
   ▼
 nginx ──► frontend (статика)
   │ /api, /ws
   ▼
  api ──► postgres
   │  └─► livekit ◄── браузер (голос, WebRTC 7880–7882)
   │         ├─► egress ──► ./recordings/*.ogg
   │         └─► agent ──► Yandex AI Studio (распознавание, модель, синтез)
   └─► MAX Bot API (сообщения бота, если задан токен)
```

Backend устроен как модульный монолит: `identity` (вход), `catalog` (описание услуги), `applications` (заявление), `assist` (встреча, права, проекция формы, WebSocket), `trust` (близкие), `support_desk` (очередь МФЦ), `voice` (комнаты и записи), `notifications` (бот), `ai_assistant` (цифровой сотрудник).

## Запуск одной командой

Нужен только Docker. Из корня репозитория:

```bash
docker compose --profile local up -d --build
```

Если в `.env` в корне указано `COMPOSE_PROFILES=local`, достаточно `docker compose up -d --build`.

Через 1–2 минуты после окончания сборки откройте `http://localhost:3000`. Проверить, что backend готов:

```bash
curl -fsS http://localhost:3000/health
```

## Требования к окружению

- Docker Engine 24+ и Docker Compose v2.20+ (Docker Desktop на Windows и macOS тоже подходит, в режиме Linux-контейнеров).
- Процессор x86-64 или ARM64; Linux, macOS или Windows.
- Свободно не меньше 4 ГБ оперативной памяти для контейнеров и 8 ГБ на диске для образов.
- Доступ в интернет во время сборки: скачиваются пакеты Python и npm.
- Свободные порты из раздела «Порты».
- Современный браузер (Chrome, Edge, Firefox, Safari) и микрофон — для проверки голоса.

## Внешние сервисы и интеграции

| Сервис | Зачем | Что будет без него |
|---|---|---|
| MAX (mini app и MAX Bridge) | Вход по подписанному `initData`, сканер QR, отправка ссылок | Локально вход идёт через экран тестовых пользователей, сканер QR заменяет ввод ссылки вручную |
| MAX Bot API (`platform-api.max.ru`) | Сообщения близкому: «Подключиться», «Сейчас не могу», «Освободился» | Все сообщения бота видны в dev-ящике на экране входа, кнопки в нём работают так же |
| Yandex AI Studio: SpeechKit и модель Qwen | Цифровой сотрудник: распознавание речи, ответ модели, синтез голоса | Кнопка «Цифровой сотрудник» отвечает «сейчас недоступен», остальное работает |
| Публичные STUN-серверы | LiveKit узнаёт свой внешний адрес | Для браузера на том же компьютере не нужны |

**Что нельзя воспроизвести внутри Docker.**

- **MAX.** Mini app открывается внутри мессенджера по HTTPS-адресу, зарегистрированному за ботом, а вход проверяется по подписи токена бота. Поэтому сценарий именно в MAX проверяется на рабочей версии: откройте `https://max.ru/t562_hakaton_max_bot` и запустите mini app. Локальный стенд проходит тот же сценарий в обычном браузере под тестовыми пользователями.
- **Yandex AI Studio.** Цифровому сотруднику нужен ключ сервисного аккаунта с ролями `ai.models.user`, `ai.languageModels.user`, `ai.speechkit-stt.user`, `ai.speechkit-tts.user`. Впишите его в `.env` как `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` и перезапустите стенд. Без ключа эта часть недоступна, но на рабочей версии в MAX она включена.

## Работа с данными

- **Где хранится.** PostgreSQL в томе `pgdata`, записи встреч — файлы `.ogg` в каталоге `recordings/` в корне репозитория. Схема создаётся миграциями Alembic при каждом старте API; демо-услуга добавляется миграцией.
- **Личные данные.** Поля формы делятся на публичные и личные по описанию услуги. Личные значения (ФИО, дата рождения, СНИЛС, адрес, доход, счёт) хранятся в базе в зашифрованном виде (Fernet, ключ `FIELD_ENCRYPTION_KEY`).
- **Что видит помощник.** Сервер отдаёт каждому участнику свою проекцию формы: помощник получает «заполнено / не заполнено» вместо значения, а поля «только владельцу» приходят заблокированными. Цифровой сотрудник получает ту же проекцию, поэтому личные данные не попадают и в модель.
- **Журнал встречи.** Сохраняются действия (переход по шагам, подсветки, «непонятно»), но не значения полей. Расшифровка речи человека не хранится; от цифрового сотрудника сохраняется только то, что он сказал сам.
- **Сроки хранения.** Раз в час удаляются демо-SMS старше 24 часов, приглашения старше 7 дней, брошенные черновики через 30 дней, отправленные заявления через 90 дней. Встречи и записи автоматически не удаляются: к ним возвращаются при повторной подаче услуги. Владелец может удалить запись сам.

## Тестовые данные

Отдельно загружать ничего не нужно: демо-услуга создаётся миграцией, тестовые пользователи — при первом входе.

| Пользователь на экране входа | Роль | Для чего |
|---|---|---|
| Людмила Петрова | гражданин | Заполняет заявление и зовёт помощь |
| Сергей Клосеп | близкий | Помогает Людмиле |
| Анна Смирнова | сотрудник МФЦ | Берёт обращения из очереди |
| Олег Нечаев | посторонний | Проверка защиты: чужой по пересланной ссылке |

- **Экран входа.** Появляется при открытии `http://localhost:3000` в обычном браузере. Каждая вкладка — отдельный вход, поэтому двух пользователей удобно проверять в двух вкладках.
- **Демо-услуга** «Компенсация расходов на оплату ЖКУ»: подходят значения вида СНИЛС `123-456-789 00`, площадь `54.5`, индекс `190000`.
- **Код из SMS** настоящим SMS не приходит: на последнем шаге он показывается уведомлением, повторно — по кнопке «Показать демо-SMS».
- **Сообщения бота** видны на экране входа выбранного пользователя в блоке «Сообщения бота», кнопки в нём открывают нужный экран.
- **Очистить свои данные** можно из Swagger (`http://localhost:8000/docs`, `POST /api/v1/dev/reset`), а удалить всё — командой из раздела «Остановка и повторный запуск».

## Пошаговый сценарий проверки

**1. Запуск.** Выполните `docker compose --profile local up -d --build`, затем `curl -fsS http://localhost:3000/health`.
Ожидается: `{"status":"ok","db":"ok",…,"livekit":"ok",…}`.

**2. Заявление.** Откройте `http://localhost:3000`, выберите «Людмила Петрова» → «Открыть приложение» → «Начать». Пройдите шаги; на последнем введите код из уведомления (повторно — кнопка «Показать демо-SMS») и нажмите «Отправить заявление».
Ожидается: при пустом обязательном поле «Далее» показывает ошибку под полем; после отправки — «Заявление отправлено» с номером вида `ЖКУ-2026-000001`.

**3. Позвать близкого.** В первой вкладке начните новое заявление, на любом шаге нажмите «Позвать помощь», согласитесь на запись и выберите «Отправить ссылку». Скопируйте из ссылки часть после `startapp=` (начинается с `as_`). Во второй вкладке откройте `http://localhost:3000`, выберите «Сергей Клосеп», вставьте эту часть в поле «Проверить deep link» и нажмите «Проверить ссылку» → «Подключиться». В первой вкладке нажмите «Разрешить».
Ожидается: перед «Разрешить» Людмила видит предупреждение о мошенничестве; у Сергея открывается режим помощника с шагом Людмилы.

**4. Приватность и подсветка.** Людмила заполняет ФИО и СНИЛС. Сергей выбирает инструмент «Подсветка» и нажимает на поле.
Ожидается: у Сергея вместо значений — «███ заполнено» и «Доступно только владельцу»; у Людмилы поле подсвечивается с подписью от Сергея.

**5. Голос и запись.** Оба нажимают кнопку микрофона и разрешают доступ. Лучше в наушниках, иначе будет эхо: вкладки на одном компьютере.
Ожидается: собеседники слышат друг друга, в панели встречи горит «Идёт запись». После «Завершить помощь» у Людмилы в «История помощи» появляется встреча, и её можно прослушать.

**6. «Сейчас занят».** Повторите шаг 3, но во вкладке Сергея нажмите «Сейчас занят».
Ожидается: Людмила видит «Помощник сейчас занят» и может сохранить черновик. На экране входа Сергея в «Сообщения бота» есть кнопка «Теперь могу помочь»; после неё у Людмилы на главной появляется «Сергей готов помочь».

**7. Сотрудник МФЦ.** Людмила: «Позвать помощь» → «Сотрудник МФЦ» → тема. В другой вкладке войдите как «Анна Смирнова» → «Очередь обращений» → «Взять в работу».
Ожидается: Людмила видит свою позицию в очереди, после взятия Анна подключается с бейджем «Сотрудник МФЦ».

**8. Близкий по QR или ссылке.** Людмила: «Мои близкие» → «Добавить по ссылке». Во вкладке Сергея: «Кому я помогаю» → «Вставить ссылку вручную» → «Принять». Людмила нажимает «Подтвердить».
Ожидается: Сергей появляется в списке близких, а его можно звать одним нажатием из «Позвать помощь».

**9. Цифровой сотрудник** (нужен ключ Yandex AI Studio в `.env`). Людмила: «Позвать помощь» → «Цифровой сотрудник», затем спросите голосом «Какое основание получения льготы мне выбрать?».
Ожидается: через 1–3 секунды после вопроса звучит короткий ответ женским голосом, и нужное поле подсвечивается. Без ключа — сообщение «Цифровой сотрудник сейчас недоступен».

**10. Защита от посторонних.** Скопируйте приглашение, как в шаге 3, но войдите во второй вкладке как «Олег Нечаев».
Ожидается: Олег не видит форму, пока Людмила не нажмёт «Разрешить»; кнопка «Отклонить» закрывает ему доступ.

## Примеры ожидаемого поведения

```bash
curl -fsS http://localhost:3000/health
```

```json
{"status": "ok", "db": "ok", "db_size_mb": 8, "livekit": "ok", "recordings_size_mb": 0}
```

- Без согласия на запись позвать помощь нельзя: API отвечает `409 recording_consent_required`, а интерфейс показывает галочку согласия.
- Помощник, пытающийся подсветить поле другого шага, получает ошибку `unknown_element`. Кнопок для заполнения полей и отправки у него нет, а прямой запрос к API на изменение чужого заявления получит `403`.
- Приглашение, отправленное ботом конкретному человеку, не сработает у того, кому его переслали: `403`.
- Если в голосовую комнату никто не вошёл, запись получает статус `failed` и не показывается как доступная к прослушиванию.
- Без ключа Yandex AI Studio `POST /api/v1/assist-sessions/{id}/ai-agent` отвечает `503 digital_employee_unavailable`.

## Автоматическая проверка API

[DATA-API.yaml](DATA-API.yaml) описывает обязательные проверки по формату DATA-API 1.0: доступность сервиса, профиль, каталог услуг, заявление (создать, заполнить шаг, прочитать) и сессию помощи. После проверок заявление и сессия помощи удаляются. Пути сверяются с [openapi.yaml](openapi.yaml) — он выгружается из кода backend:

```bash
cd backend
python export_openapi.py
```

Все проверки, кроме `/health`, выполняются с ролью `user`: запросы идут с заголовком `Authorization: Bearer <токен>`. Токен выдаёт `POST /api/v1/auth/review-login` с логином и паролем — это отдельный пользователь «Проверка Ж.», он не видит данных других людей. Вход работает и в production, но только когда в `.env` задан `REVIEW_PASSWORD` длиной от 16 символов. Пароль передаётся организаторам отдельно, в репозитории его нет. Логин, формат входа и значения всех шагов формы — в [test-data/review.json](test-data/review.json).

## Известные ограничения

- Демо-услуга одна и не связана с настоящими Госуслугами: заявление никуда не отправляется, код из SMS показывается в приложении.
- Вход в MAX по `initData` работает только внутри MAX на рабочей версии; локально используется вход тестовыми пользователями.
- Голос с другого устройства (телефона) требует HTTPS и `LIVEKIT_NODE_IP` с адресом компьютера в сети; на `localhost` браузер разрешает микрофон без HTTPS.
- Цифровому сотруднику нужен ключ Yandex AI Studio и доступ в интернет; задержка ответа зависит от Яндекса и обычно составляет 2–3 секунды после паузы.
- Сканер QR-кода есть только в MAX; в браузере вместо него — ввод ссылки вручную.
- Egress сообщает, что для видеозаписи рекомендуется 4 ядра; для записи только звука хватает двух.
- API работает в одном процессе: состояние встреч в WebSocket хранится в памяти процесса.

## Остановка и повторный запуск

Остановить, сохранив данные:

```bash
docker compose --profile local stop
```

Запустить снова без пересборки:

```bash
docker compose --profile local up -d
```

Пересобрать после изменения кода:

```bash
docker compose --profile local up -d --build
```

Остановить и удалить контейнеры, сохранив базу и записи:

```bash
docker compose --profile local down
```

Удалить всё, включая базу (записи в `recordings/` удаляются отдельно):

```bash
docker compose --profile local down -v
```

Для одноразового Docker-прогона, запущенного через `make deploy-local`, используйте `make local-clean`: команда удалит контейнеры, сеть, созданные Compose локальные образы и оба named volume (`pgdata`, `local_recordings`). Она повторно задаёт локальные параметры и не использует production-секреты из корневого `.env`. Обычные `docker compose stop`, `make local-down` и `docker compose down` данные намеренно сохраняют. `local-clean` не удаляет общие базовые образы Docker и build cache; для них не запускайте глобальный `docker system prune`, если на машине есть другие проекты.

Логи:

```bash
docker compose --profile local logs -f api agent egress
```

Те же действия с проверкой готовности есть в `Makefile` (`make deploy-local`, `make local-down`, `make local-clean`, `make local-logs`) — для систем, где установлен GNU Make.

## Разработка без Docker

Backend (Python 3.12) — подробности в [backend/README.md](backend/README.md):

```bash
cd backend
python -m pytest
python -m ruff check src tests
```

Frontend (Node 22):

```bash
cd frontend
npm ci
npm run dev
npm run build
```

Цифровой сотрудник — [agent/README.md](agent/README.md).
